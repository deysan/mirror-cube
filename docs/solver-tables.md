# Solver transitions and distance tables

## Scope

`src/solver/tables.ts` implements normalized move lookups and admissible lower bounds for the IDA* solver. It builds on the [validated coordinate encoding](state-encoding.md) and the existing exact `applyMove` rules. Search is implemented separately in [the search core](solver-search.md); worker integration and a solve button are described in the [worker guide](solver-worker.md). Animated solution playback is not yet implemented.

Both input workflows use this same foundation: manually turn/scramble the virtual cube, or later reconstruct and confirm a physical state from photographs. Neither tables nor search require the input's move history.

## API

```ts
import {
  createSolverTables, applyTableMove, estimateRemainingMoves, SOLVER_MOVES,
} from "./solver/tables";

const tables = createSolverTables();
const current = { permutation: 0, twist: 0 };
const next = applyTableMove(tables, current, 0); // normalized R
const lowerBound = estimateRemainingMoves(tables, next); // 1, not 2
const move = SOLVER_MOVES[0];
```

`createSolverTables()` is explicit and synchronous. Importing the module does not generate tables. Each call returns independently owned buffers; there is no shared mutable singleton, persistent cache, downloaded asset, or new dependency. The solver worker creates a set once and reuses it across requests, rather than rebuilding for every search. Terminating a cancelled or failed worker discards that set.

The nine columns have a stable order:

```text
R  R′  R2  U  U′  U2  F  F′  F2
```

All these moves preserve the normalized `---` reference corner. Each turn costs **one move**, including 180° turns. The inverse of every move is included, so the coordinate graphs are reversible.

The lookup helpers check coordinate and move-index integer ranges and throw `RangeError` on invalid values. They expect an intact table set from the factory; they do not validate arbitrary externally supplied table buffers. They do not mutate their inputs.

## Transition layout and construction

The table set contains:

| Buffer | Type | Entries | Layout |
| --- | --- | --- | --- |
| `permutationTransitions` | `Uint16Array` | 5,040 × 9 | `permutationRank * 9 + moveIndex` |
| `twistTransitions` | `Uint16Array` | 729 × 9 | `twistRank * 9 + moveIndex` |
| `permutationDistances` | `Uint8Array` | 5,040 | Indexed by permutation rank |
| `twistDistances` | `Uint8Array` | 729 | Indexed by twist rank |

To construct a transition row, the builder decodes a representative with the other coordinate zero, applies each exact domain move, then re-encodes the result. Invalid generated states cause construction to fail rather than producing a partially usable result.

The factors evolve independently:

- permutation changes depend on which slots the selected layer moves, not their twists;
- a corner's twist changes by the cyclic offset between the current and destination slot frames, not by the piece identity occupying that slot.

Thus a row generated with the other coordinate zero applies to arbitrary combinations of both coordinates. Tests specifically cross-check representatives with nonzero values of the other factor, not just the states used by the builder.

At lookup time, `applyTableMove` reads two integers. It does not reconstruct eight poses, apply geometric rules, or revalidate a puzzle. The full-domain path remains the independent correctness oracle.

## Distances and heuristic

Each factor's distances are generated by breadth-first traversal from solved rank zero. Unvisited entries use 255 during construction. The builder rejects disconnected graphs or distances that exceed the byte representation; no unvisited sentinel remains in a successful table set.

The observed maximum exact factor distances are **7 for permutation** and **6 for twist**. These are projected-graph distances, not a bound of seven moves for solving a complete puzzle.

The combined estimate is:

```text
h(permutation, twist) = max(permutationDistance, twistDistance)
```

Any full solution projects to a path solving each factor with the same moves. Each projected minimum is therefore a lower bound on the complete solution length; their maximum is also a lower bound. It is consistent across one-move edges because each factor distance changes by at most one.

Do **not** add the factor distances: after one R turn, both are one, but a single R′ solves the whole state. The sum would incorrectly estimate two. A lower bound is not itself a solution or necessarily the exact full-state distance.

## Ownership, initialization cost, and UI boundary

The four retained buffers total **109,611 bytes (about 107 KiB)**. This excludes object headers, temporary decoded/validated states, BFS queues, and garbage-collector overhead. Buffer properties are readonly in the interface, but JavaScript typed arrays remain mutable; callers must treat their contents as read-only after construction.

A local five-run measurement on Node.js v24.19.0 took approximately **365–454 ms per construction**. This is an observation for the development machine, not a browser/mobile performance guarantee or a test threshold. Synchronous initialization can block the main thread and must not be silently triggered by rendering a component. The implemented worker boundary keeps this initialization off the main thread.

Only the separate worker asset imports these tables at runtime; the main UI does not generate them. No generated binary table files are committed.

## Verification

`src/solver/tables.test.ts` checks:

- stable move order, buffer types/sizes, and one-move costs for every angle;
- range, inverse, four-quarter-turn, and half-turn identities over all factor rows;
- complete distance coverage, zero only at the goal, and the observed maximum distances;
- every distance edge differs by at most one and every non-goal rank has a neighbor one step closer;
- exact-move agreement at every permutation rank with a varying nonzero twist, and every twist rank at several nonzero permutations;
- a 1,000-step full-pose/lookup walk with non-mutation and heuristic consistency;
- independent full-pose breadth-first enumeration through depth four: **2,232 distinct states**, with no heuristic overestimate;
- max-versus-sum behavior, invalid lookup arguments, and independently owned deterministic table sets.

The edge inequalities and descending-neighbor checks certify the shortest-distance labels without repeating the builder's BFS: edge bounds prevent overestimation and descending paths realize each label. Existing coordinate and domain tests remain in place. The table tests do not exhaustively traverse the full 3,674,160-state Cartesian graph. The separate search tests now do so with a test-only BFS oracle; it is not part of table construction.

Run `npm test` and `npm run build`. The table module itself has no UI/rendering behavior. Search and worker/UI integration are implemented separately; animated solution playback remains the next functional step.
